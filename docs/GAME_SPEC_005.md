# Clap-Clap 五行拍手对战 · 联机版规范（V4.0）

> **版本说明**：基于 V3.1 单机规则扩展而来，主要新增联机架构规范，并对多人模式下的招式平衡性做出调整。
> 所有 V3.1 规则在 1v1 单机/联机下保持不变，下述修改仅影响 3 人及以上的多人对战。
> 若 V4.0 与 V3.1 冲突，以 V4.0 为准。

## 1. 联机架构总览

### 1.1 目标形态
- 支持 2～9 名玩家**在线联机对战**（PvP），初期优先实现 1v1 联机，再扩展至多人。
- 单机人机模式（V3.1）保留为可选项。

### 1.2 技术选型（强制）
- **后端**：Node.js + Colyseus 框架（≥0.15）。
- **通信**：WebSocket（由 Colyseus 封装）。
- **同步策略**：服务器权威的状态同步（Server-Authoritative）。
  - 客户端仅发送玩家动作指令（`{ action }`）；
  - 服务器运行完整 `GameEngine` 逻辑，生成新状态；
  - 服务器将完整游戏状态（`state`）广播给所有客户端，客户端负责渲染。
- **房间与匹配**：Colyseus 原生支持房间（`Room`），匹配逻辑可基于 `LobbyRoom` 或自定义。

### 1.3 核心流程
1. 客户端连接至服务器，加入或创建房间。
2. 房间满员后自动开始（或房主手动开始）。
3. 游戏循环与单机一致（`READY → LOCK → RESULT → READY`），但由服务器统一推进：
   - 客户端通过 `READY` 指令提交动作；
   - 服务器收集所有在线玩家的动作后，锁定并结算；
   - 结算结果广播给所有客户端。
4. 若玩家断开连接：
   - 服务器保留该玩家状态，在一定时间内（如 60 秒）允许重连；
   - 若超时或房间所有人断开，则房间销毁。

## 2. 多人平衡性调整（仅限 2+ 玩家）

以下调整基于 V3.1 规则，在多人对战中额外生效。

### 2.1 水系 · 冲刷（`scour`）与 木系 · 种子寄生（`seed`）
- **保护机制**：当一个目标被“冲刷”或“种子”成功命中后，该目标获得 **2 回合免疫期**（针对同一招式）。
  - 免疫期内，再次受到同一招式（`scour` 或 `seed`）时，攻击无效，且**不消耗攻击者资源**（如同当前束缚不可叠加的处理）。
  - 免疫期以目标受击后的下一个回合开始计算，持续 2 个整回合（例如第 N 回合被命中，则第 N+1、N+2 回合免疫，第 N+3 回合可再次生效）。
  - 两种免疫独立计算（冲刷免疫和种子免疫互不影响）。
- 在 UI 中应显示“免疫冲刷”和“免疫种子”的图标及剩余回合。

### 2.2 木系 · 藤蔓束缚（`bind`）
- **维持不可叠加**（V3.1 已有）。
- **新增免疫期**：束缚解除后（无论是自然结束、挣脱还是受击断裂），目标获得 **1 回合免疫束缚**（即下一次被施加 `bind` 时将失效且不消耗资源）。
  - 免疫期从解除束缚的下一回合开始计算，持续 1 个整回合。
  - 该免疫仅针对束缚，不影响其他控制。

### 2.3 金系 · 穿甲弹（`apFire`）
- **增强对反伤技能的克制**：
  - 穿甲弹命中**荆棘之墙**时，除原有“击碎墙、伤害+1、无反弹”外，**额外使该目标本回合的荆棘岩和岩脉共鸣反伤失效**（相当于清空其反伤能力）。
  - 穿甲弹命中**荆棘岩**时，无视岩壳、正常造成伤害，**且额外消耗目标 1 层岩壳**（若有）。
- 上述效果在 V3.1 中已有部分体现，现明确强化。

### 2.4 火系 · 烈焰爆发（`blaze`）
- **不做调整**，维持高风险高收益特性（3 伤 + 自伤 1 无视防御）。

### 2.5 金系 · 双枪射击（`dualFire`）
- **多人分流规则不变**：在 3+ 人局中，必须指定两个不同目标；1v1 时可集火同一目标造成 2 伤。
- 这是其战略取舍的核心设计，无需改动。

## 3. 网络协议与数据格式

### 3.1 客户端 → 服务器
- **连接**：`client.join(roomName, options)` 时，携带玩家名称。
- **动作提交**：通过 `room.send('action', actionData)` 发送动作，其中 `actionData` 格式与单机一致：
  ```javascript
  { type: 'gather' | 'use' | 'defend', element, route, amount, targets }
准备就绪：room.send('ready') 表示已选好动作，可进入锁定阶段。

3.2 服务器 → 客户端
状态广播：room.onStateChange 推送完整的 GameState 对象（包含所有玩家数据、回合信息、战报等）。

战报消息：通过 room.onMessage('report') 推送当前回合的详细结算（含日志、伤害变化等）。

4. 服务器端职责
托管 GameEngine 实例（每个房间一个）。

维护房间状态（玩家列表、游戏是否开始等）。

处理客户端动作，调用引擎的 submitAction(playerId, action) 和 runTurn()。

广播状态。

管理断线重连（利用 Colyseus 的 onLeave 和 allowReconnection()）。

5. 客户端职责（UI 层）
保持与单机相似的界面，但需增加：

房间列表/创建/加入界面；

对手信息（名称、HP、元素、状态等）；

当前回合倒计时或等待对手准备的状态提示；

断线重连提示。

网络层：封装 Colyseus 客户端，监听状态变化并更新 UI。

6. 测试与验收标准
支持 2～9 人联机（至少 2 人）。

平衡调整生效：免疫机制、穿甲弹克制等均在多人局中正确触发。

断线重连后状态恢复正确。

多人局无作弊可能（服务器权威）。

单机人机模式仍可独立运行（不依赖网络）。

7. 迁移路径
将 engine.js 中的 GameEngine 类抽离为独立 npm 包，供前后端共用。

构建 Colyseus 服务器，引入引擎并实现房间逻辑。

改造原前端，引入 Colyseus 客户端，替换本地引擎调用。

完善 UI 交互（房间、状态提示等）。

测试并迭代。
